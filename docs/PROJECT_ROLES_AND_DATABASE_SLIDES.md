1. «Это NotificationService — REST API для создания и хранения уведомлений пользователей. В этом видео я разберу участников системы, схему базы данных, технологии и слои приложения, доменные правила и тесты. Затем покажу полный путь создания уведомления: от HTTP-запроса до записи в PostgreSQL».

2. «В системе есть пользователи и администраторы. Пользователь является получателем уведомлений: API позволяет получить его уведомления, отфильтровать непрочитанные, узнать их количество, а также отметить уведомление прочитанным или вернуть в непрочитанное состояние.

Администратор может быть указан в уведомлении как отправитель, но эта связь необязательна. Для пользователей и администраторов также предусмотрены операции создания, просмотра, изменения и удаления.

Важно: здесь описаны сущности и операции API, а не защищённые роли. Аутентификация и проверка прав доступа в проекте пока не настроены. Основная сущность сервиса — уведомление. В проекте нет новостной ленты, публикационных статусов, комментариев или реакций».

3. «На ER-диаграмме показана база данных NotificationService. Главная таблица — `Notifications`. Каждое уведомление обязательно связано с одним пользователем-получателем, а у пользователя может быть много уведомлений.

Связи с администратором и `RelatedEntity` необязательны. Таблица `RelatedEntities` хранит дополнительный контекст, например отображаемое имя объекта и внешний URL. Тип этого объекта хранится отдельно, в поле `RelatedEntityType`.

В `Notifications` также находятся заголовок, текст, тип уведомления, дата создания и состояние прочтения. При удалении администратора или связанной сущности уведомление остаётся, а соответствующая ссылка очищается. Удалить пользователя, на которого ссылаются уведомления, нельзя, пока такие уведомления существуют».

4. «Технически проект написан на C# и .NET 8. HTTP API построено на ASP.NET Core Controllers. Данные хранятся в PostgreSQL, доступ к ним организован через Entity Framework Core и провайдер Npgsql. AutoMapper преобразует доменные сущности в модели API, а Swagger описывает и позволяет вручную вызывать HTTP-методы.

Сервис отвечает за отдельную область — уведомления — и может быть одним из микросервисов более крупной системы. При этом в данном репозитории находится одно WebHost-приложение с несколькими внутренними слоями, а не набор независимо развёртываемых сервисов. Брокер сообщений и отдельные службы отправки email или push здесь не настроены.

Presentation содержит точку входа и контроллеры. Application содержит сценарии работы и модели запросов и ответов. Domain описывает сущности и бизнес-правила. Infrastructure реализует репозитории и сохранение в базе. Тесты находятся в отдельном проекте.

Схему PostgreSQL создают и обновляют миграции EF Core. При старте WebHost вызывается `MigrateDatabase`, который применяет ожидающие миграции через `Database.Migrate()`. Начальная миграция создаёт таблицы пользователей, администраторов, связанных сущностей и уведомлений, а также внешние ключи и индексы.

Создание уведомления проходит по цепочке: контроллер `NotificationsController.Create` вызывает `NotificationApplicationService.CreateModelAsync`. Сервис проверяет получателя и дополнительные связи, создаёт доменный объект и передаёт его репозиторию. Реализация `EfRepository.AddAsync` добавляет объект в контекст и сохраняет изменения через `SaveChangesAsync`. Теперь рассмотрим сам доменный объект и его методы».

5. «Центральная доменная сущность — `Notification`. Она хранит получателя, необязательного администратора, заголовок, текст, тип, дату создания, необязательную связанную сущность и состояние прочтения.

Новое уведомление создаётся непрочитанным: `IsRead` равно `false`, а `ReadAt` не задано. Метод `MarkAsRead` устанавливает состояние прочитанного и записывает время. Метод `MarkAsUnread` снимает отметку и очищает время прочтения. Если уведомление уже находится в требуемом состоянии, повторный вызов не изменяет его.

Метод `Update` позволяет изменить получателя и содержимое уведомления. `User` хранит имя пользователя и предоставляет операции отметки уведомления прочитанным или непрочитанным. `Administrator` может создать уведомление и управлять связанными с ним уведомлениями. `RelatedEntity` хранит отображаемое имя и внешний URL связанного объекта.

Для заголовка, текста, имён и типа связанной сущности используются Value Objects. Они проверяют данные, например пустые значения и допустимую длину. Тип уведомления — enum: `Info`, `Warning`, `Success` или `Error`. В текущем JSON он передаётся числом: `0` — Info, `1` — Warning, `2` — Success, `3` — Error.

Доменный слой не знает о HTTP и PostgreSQL. Его правила можно проверять отдельно от инфраструктуры. Следом посмотрим, какие из этих сценариев проверяют автоматические тесты».

6. «В тестовом проекте сейчас 39 тестов, и последний запуск завершился успешно. Тесты проверяют доменные правила, валидацию Value Objects, application-сервисы и преобразование сущностей в модели API.

По последнему Cobertura-отчёту line coverage составляет 95,83 процента — покрыты 414 из 432 измеряемых строк. Это показатель кода, который входит в текущий тестовый охват; WebHost и EF-инфраструктура в него полностью не включены.

GitHub Actions собирает решение и запускает тесты при push или pull request в ветки `main` и `master`, а также вручную. Workflow требует не менее 80 процентов покрытия и загружает Cobertura-файл как artifact. HTML-отчёт формируется локально через ReportGenerator; сам workflow HTML сейчас не генерирует.

Теперь проверим путь запроса на практике: создадим уведомление через Swagger и найдём его в базе».

7. «В Swagger открываю `POST /api/notifications`. В запросе указываю ID существующего пользователя, заголовок, текст и тип уведомления. Для типа `Info` передаю значение `0`. Администратора и связанную сущность в этом примере не указываю, потому что эти связи необязательны.

После отправки контроллер вызывает application-сервис. Сервис убеждается, что пользователь-получатель существует, создаёт новое доменное уведомление и передаёт его репозиторию. Entity Framework Core сохраняет запись в PostgreSQL. При успехе API возвращает статус `201 Created` и данные созданного уведомления.

Теперь открываю таблицу `Notifications`. В ней появилась запись с ID, получателем, заголовком, текстом, типом, датой создания и начальным состоянием непрочитанного. Затем вызываю `GET /api/notifications` с фильтром по `userId` и вижу это уведомление в ответе API.

Для проверки состояния вызываю `PATCH /api/notifications/{id}/read`. Уведомление отмечается прочитанным, а в записи появляется время `ReadAt`. Так один сценарий проходит от Swagger через контроллер, application-сервис и репозиторий до PostgreSQL».

8. «Итак, мы проследили весь путь уведомления: от HTTP-запроса и доменных правил до записи в PostgreSQL. Архитектурные слои разделяют ответственность, тесты проверяют ключевые сценарии, а GitHub Actions автоматически контролирует сборку и минимальный порог покрытия».
