# 4. Введение

## 4.1 Актуальность темы

Современные информационные системы для массовых пользователей всё чаще строятся как **набор слабо связанных микросервисов**. Такой подход упрощает независимое развёртывание и масштабирование отдельных частей, но порождает потребность в **сквозных пользовательских сценариях**, где данные и события приходят из разных контекстов. Для платформы проведения турниров критично своевременно информировать участников и организаторов: изменения расписания, статус матча, системные предупреждения, действия администрации. Выделение **сервиса уведомлений** в отдельный ограниченный контекст позволяет:

- не перегружать доменные модели турниров и матчей второстепенной логикой доставки сообщений пользователю;
- накапливать и отображать **историю коммуникаций** в одном месте;
- единообразно учитывать **прочитанность** и тип сообщения для клиентских приложений;
- в перспективе подключать каналы доставки (push, e-mail, SMS) за стабильным API.

Актуальность сочетается с методической: реализация на **.NET 8**, **EF Core 8** и **PostgreSQL** демонстрирует распространённый промышленный стек и приёмы сопоставления **богатой доменной модели** с реляционной схемой без «анемичной» модели только DTO.

## 4.2 Объект и предмет исследования

**Объект исследования** — программное обеспечение микросервисной платформы проведения турниров (логическая экосистема сервисов и их взаимодействие).

**Предмет исследования** — проектирование и реализация микросервиса **Eventide.NotificationService**: предметная область, требования, архитектурные решения (DDD, Clean Architecture), доменный слой, инфраструктурный слой на базе EF Core, демонстрационное консольное приложение и веб-хост.

## 4.3 Цели и методы

**Цель** сформулирована в реферате. **Методы:** анализ исходного кода и структуры репозитория; сравнение с рекомендациями Microsoft по микросервисам и слоистой архитектуре; концептуальное моделирование связей между сервисами; обобщение по учебной литературе по DDD и Clean Architecture.

## 4.4 Практическая и научная новизна

Практическая новизна — в **целостном описании** реального учебно-промышленного фрагмента платформы: от границ контекста до деталей конфигурации EF (конвертации value objects, теневые внешние ключи, индексы). В рамках курсовой работы новизна не претендует на научную публикацию, но фиксирует **осознанный выбор** инженерных компромиссов (например, немедленный `SaveChangesAsync` в базовом репозитории вместо unit-of-work).

# 5. Описание объекта автоматизации и требований к создаваемой программе

## 5.1 Проблема автоматизации и место NotificationService

### 5.1.1 Суть объекта автоматизации

**Объект автоматизации** в данной работе — процесс информирования пользователей платформы проведения турниров о событиях, требующих их внимания: изменения в расписании, исходы матчей, системные предупреждения, действия администрации, приглашения и ответы на заявки. До внедрения выделенного сервиса эта функция либо **отсутствует** как единая подсистема, либо **расползена** по нескольким приложениям: каждый микросервис вынужден хранить собственные «сообщения» или дублировать каналы связи, что ухудшает сопровождение и согласованность интерфейса.

### 5.1.2 Заинтересованные стороны и их ожидания

| Стейкхолдер | Ожидание от подсистемы уведомлений |
|-------------|-----------------------------------|
| Участник турнира | Единая лента, понятные типы сообщений, признак прочтения, ссылки на матч/турнир |
| Администратор платформы | Возможность рассылать системные сообщения, контроль созданных уведомлений |
| Команда разработки | Слабая связность с другими сервисами, тестируемый домен, предсказуемая схема БД |
| Эксплуатация | Миграции схемы, логирование, отсутствие утечки чувствительных данных в prod |

### 5.1.3 Цели автоматизации в терминах требований

1. **Централизация:** один источник истины по пользовательским уведомлениям в границах bounded context «Notifications».
2. **Согласованность:** идентификатор пользователя и опционально внешнего объекта согласуются с контрактами UserService и доменных сервисов турниров/матчей.
3. **Расширяемость:** возможность подключить асинхронную доставку и новые каналы без переписывания доменной модели.

Автоматизация через **единый микросервис уведомлений** сводит пользовательский опыт к одному API и одной модели данных в контексте «сообщение пользователю», снижая дублирование кода и расхождение UX.

## 5.2 Контекст платформы: взаимосвязи микросервисов

### 5.2.1 Логическая карта сервисов

Реализация всех перечисленных компонентов в одном репозитории не требуется; для курсовой важна **роль каждого** относительно NotificationService и **направление зависимостей** на уровне бизнес-процессов (кто инициирует создание уведомления).

| Микросервис | Назначение (кратко) | Связь с NotificationService |
|-------------|---------------------|-------------------------------|
| **Auth-Service** | Аутентификация, токены, идентификация субъекта | Передаёт доверенный идентификатор пользователя/роли в запросах к API уведомлений |
| **UserService** | Профиль, уникальность имени пользователя | Обеспечивает согласованность `User.Id` и `Username` с данными, которые отображаются в уведомлениях |
| **TournamentService** | Турниры, регламент, заявки | Источник событий «заявка», «статус турнира» → создание уведомлений (интеграция) |
| **BracketService** | Сетка, переходы по стадиям | События смены стадии/пары → уведомления участникам |
| **MatchService** | Матчи, результаты, переносы | Основной источник спортивно-игровых уведомлений |
| **NotificationService** | Реестр уведомлений, прочитанность, типы | Потребляет **идентификаторы** и **типы** внешних сущностей (`RelatedEntity`), не дублируя турнирную логику |

### 5.2.2 Виды взаимодействия (синхронные и асинхронные)

**Синхронный вызов (HTTP/gRPC):** клиент или BFF запрашивает ленту уведомлений, отмечает прочитанным; админ-панель создаёт уведомление через API. Подходит для операций, требующих немедленного ответа и простой модели ошибок.

**Асинхронная интеграция (очередь событий):** MatchService после фиксации результата публикует событие `MatchCompleted`; NotificationService подписан и создаёт запись уведомления. Так снижается связность в рантайме и допускается временная недоступность одного из сервисов при повторной доставке сообщений. В текущей версии репозитория акцент сделан на **домене и персистентности**; шина событий описывается как **целевое** архитектурное расширение.

### 5.2.3 Поток данных (концептуально)

Внешний сервис фиксирует факт в своей БД → публикует интеграционное событие или вызывает API NotificationService → создаётся запись `Notification` с привязкой к `User` и, при необходимости, к `RelatedEntity` (например, идентификатор матча). Клиент (web/mobile) запрашивает ленту уведомлений и отмечает прочитанное. NotificationService **не пересчитывает** турнирную таблицу и **не хранит** правила жёсткой сетки — он лишь **отображает** факт, переданный из авторитетного контекста.

## 5.3 Предметная область в детализации

### 5.3.1 Унифицированный язык (Ubiquitous language)

- **Уведомление** — сообщение для пользователя с заголовком, текстом, типом (информация, предупреждение, успех, ошибка), временем создания, признаком и временем прочтения.
- **Получатель** — зарегистрированный **пользователь** (`User`).
- **Системное уведомление** — созданное **администратором** (`Administrator`); в модели сохраняется связь с автором (опционально на уровне БД через FK).
- **Связанная сущность** — логическая ссылка на объект из другого контекста: хранится идентификатор (`RelatedEntity`) и строковый **тип связи** (`RelatedEntityTypeName`), чтобы клиент мог открыть нужный экран (матч, турнир и т.д.).
- **Тип уведомления (`NotificationType`)** — перечисление, задающее семантику для UI (цвет, иконка, приоритет отображения).

### 5.3.2 Сущности и ответственность

**User** — сущность-получатель. Помимо идентификатора и `Username`, содержит поведение `MarkAsRead(Notification)`: проверка на null, запрет повторного прочтения, делегирование `Notification.MarkAsRead(DateTime.UtcNow)`. Так достигается явная **координация** сценария «пользователь прочитал» через доменный API, а не через набор «сеттеров» извне.

**Administrator** — сущность-источник системных уведомлений. Метод `CreateNotification` формирует экземпляр `Notification` с передачей ссылки на себя (`this`) в конструктор; ведёт коллекцию `_notifications` для учебной демонстрации. `DeleteNotification` удаляет уведомление из коллекции автора. В продуктивной системе коллекция в памяти администратора могла бы быть заменена полностью персистентной моделью «все уведомления, созданные данным admin id», что уже отражено в репозитории `GetNotificationsByAdministratorIdAsync`.

**Notification** — центральная сущность с богатым поведением: конструкторы для создания и восстановления из хранилища, `Update(...)` для смены содержимого и связей, `MarkAsRead` / `MarkAsUnread` с булевым результатом (идемпотентность), `ToString` для отладки. Инварианты частично усилены доменными исключениями в других методах (см. пакет `Exceptions`).

**RelatedEntity** — минимальная сущность-заглушка под GUID внешнего объекта; в EF выступает самостоятельной таблицей/строкой для FK. Смысл: **не подменять** домен Match/Tournament локальными копиями данных, а хранить только **идентичность** внешнего объекта.

### 5.3.3 Объекты-значения и валидация

`Title` и `Body` наследуют `ValueObject<string>`: при создании вызывается валидатор (`TitleValidator`, `BodyValidator`). Для заголовка заданы **минимальная и максимальная длина** (в коде: `MIN_LENGTH`, `MAX_LENGTH` для `Title`), что защищает UI и БД от некорректных данных до уровня домена. `Username` и `RelatedEntityTypeName` устроены аналогично. Таким образом, некорректное состояние **не может быть выражено** валидным value object — это классический приём DDD, снижающий количество проверок «на границе» API.

### 5.3.4 Границы агрегатов и согласованность

**Агрегат** — минимальная единица транзакционной согласованности. В модели курсового проекта ключевым агрегатом выступает **`Notification`**: изменения `IsRead` / `ReadAt` должны быть атомарны с точки зрения бизнес-смысла «одно сообщение — одно состояние прочтения». Коллекция уведомлений у `Administrator` в памяти служит учебной иллюстрацией фабрики; в БД связь «администратор — много уведомлений» реализована через FK и запрос `GetNotificationsByAdministratorIdAsync`. **Межагрегатная** согласованность (например, «удалить пользователя и все его уведомления одной транзакцией») определяется политикой продукта: текущая схема запрещает удаление пользователя при наличии уведомлений (`Restrict`), что защищает историю.

### 5.3.5 Отличие доменной модели от DTO

DTO (Data Transfer Object) предназначены для передачи данных между процессами и **не обязаны** содержать поведение. В данном проекте доменные классы **намеренно не анемичны**: операции прочтения и создания инкапсулированы внутри сущностей. Это повышает стоимость начального проектирования, но упрощает сопровождение при росте правил.

## 5.7 Сценарии использования (формализованные описания)

### UC-1. Просмотр ленты уведомлений

| Элемент | Описание |
|---------|----------|
| Актор | Пользователь (через клиентское приложение) |
| Предусловия | Пользователь аутентифицирован; известен `userId` |
| Основной поток | 1) Клиент запрашивает список. 2) Сервис выполняет запрос к БД с фильтром по получателю. 3) Возвращается список, отсортированный по `CreatedAt` по убыванию. |
| Альтернатива A1 | Запрос с `onlyUnread = true` — шаг 2 дополняется условием `IsRead == false`. |
| Постусловия | Данные в БД не изменяются. |

### UC-2. Отметить уведомление прочитанным

| Элемент | Описание |
|---------|----------|
| Актор | Пользователь |
| Предусловия | Уведомление существует и принадлежит данному пользователю (проверка на уровне приложения/API) |
| Основной поток | 1) Загрузка `Notification`. 2) Вызов `User.MarkAsRead` или `MarkAsRead` на агрегате. 3) Сохранение изменений в БД. |
| Альтернатива A1 | Уже прочитано — метод возвращает `false`, повторная запись `ReadAt` не выполняется. |
| Поток ошибок E1 | Уведомление не найдено или чужое — отказ с кодом 404/403 (реализуется на уровне API). |

### UC-3. Создание системного уведомления

| Элемент | Описание |
|---------|----------|
| Актор | Администратор |
| Предусловия | Администратор аутентифицирован и уполномочен |
| Основной поток | 1) Валидация `Title`/`Body` при создании VO. 2) `CreateNotification`. 3) `AddAsync` в репозитории / `SaveChanges`. |
| Расширение | Передача `RelatedEntity` и типа связи для deeplink в клиенте. |

### UC-4. Инициация уведомления внешним сервисом (целевое)

В текущем репозитории задел под **Contracts**; полная шина событий не реализована. В продуктивной системе: consumer очереди или HTTP handler, идемпотентный ключ события, повторная обработка без дубликатов уведомлений.

## 5.8 Модель данных и целостность в БД

### 5.8.1 Связи и каскады

Для `Notification` заданы связи: к `User` (обязательно, удаление ограничено `Restrict` — нельзя удалить пользователя, пока есть уведомления), к `Administrator` и `RelatedEntity` (необязательно, `SetNull` при удалении связанной строки — поведение настраивается под политику продукта: например, сохранять текст уведомления даже после удаления внешнего «якоря»). Индексы на `CreatedAt`, `IsRead`, `RecipientUserId`, `AdministratorId` поддерживают типовые шаблоны запросов: лента по пользователю, фильтр непрочитанных, выборки по автору.

### 5.8.2 Уникальность пользователя

Для `User` настроен **уникальный индекс** по `Username` (конвертация value object в колонку строки), что согласуется с предположением UserService о глобальной уникальности имени в рамках платформы и позволяет эффективно искать пользователя по имени (`GetUserByUsernameAsync`).

### 5.8.3 Логическая схема атрибутов сущности «Уведомление»

| Атрибут (логический) | Назначение |
|----------------------|------------|
| Идентификатор | Суррогатный ключ `Guid` |
| Заголовок / текст | Содержимое для пользователя (VO) |
| Тип | Семантика отображения |
| Прочитано / момент чтения | Состояние и аудит прочтения |
| Создано | Порядок в ленте, аналитика |
| Получатель | Обязательная связь с `User` |
| Автор | Опциональная связь с `Administrator` |
| Связанная сущность | Опциональная связь с `RelatedEntity` + строка типа |

## 5.9 Требования к информационной безопасности и персональным данным (обзорно)

Текст и заголовок уведомления могут содержать персональные или чувствительные сведения. На этапе курсового проекта зафиксированы принципы: **разграничение доступа** к ленте только владельцу (реализуется на уровне API и политик авторизации в будущем), **минимизация логирования** содержимого в production, **UTC** для однозначной интерпретации времени. Юридические аспекты (согласие на обработку ПДн, срок хранения) задаются политикой оператора платформы и выходят за рамки кода, но должны быть учтены при промышленном развёртывании.

## 5.10 Риски, ограничения и допущения текущей версии

- Отдельный **прикладной слой** (use cases, CQRS, MediatR) в решении не выделен: сценарии частично демонстрируются в `DomainApp` и предполагаются для будущих контроллеров.
- Базовый `EfRepository` вызывает `SaveChangesAsync` после каждой операции — для сложных транзакций может понадобиться **единый unit-of-work**.
- В `Program.cs` WebHost дважды вызывается регистрация Swagger — не влияет на домен, но является кандидатом на рефакторинг.
- Доменный метод `Notification.Update` в текущей версии требует не-null для опциональных связей — при расширении API потребуется согласовать контракт обновления с реальными сценариями частичного обновления.
- **Межсервисная согласованность** «событие в MatchService ↔ запись в NotificationService» в коде не показана; требуется шаблон outbox или идемпотентный consumer.

# 6. Архитектурные основы разработки

Раздел обобщает теорию, которая непосредственно **объясняет принятые в проекте решения**: почему домен отделён от EF, зачем value objects, как EF сопоставляется с DDD-моделью, как слои Clean Architecture соотносятся с микросервисом уведомлений.

## 6.1 Исторический контекст и место DDD

**Domain-Driven Design** сформулирован Эриком Эвансом как ответ на сложность предметно-ориентированных систем: вместо того чтобы начинать с таблиц БД или экранных форм, команда строит **модель предметной области**, богатую поведением и согласованную с экспертами через **единый язык** (ubiquitous language). Внедрение DDD не отменяет технических ограничений СУБД и транспорта, но задаёт **приоритет**: сначала корректные инварианты и сценарии, затем отображение на хранилище.

**Базовая литература:**

1. Evans E. *Domain-Driven Design: Tackling Complexity in the Heart of Software.* Addison-Wesley, 2003.
2. Vernon V. *Implementing Domain-Driven Design.* Addison-Wesley, 2013 — тактические шаблоны и примеры «как внедрять».

**Официальные материалы Microsoft (архитектура микросервисов и доменный анализ):**

- https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis
- https://dotnet.microsoft.com/learn/architecture-guides

## 6.2 Стратегическое проектирование: ограниченные контексты

На **стратегическом** уровне DDD система делится на **bounded context** — автономные части с собственной моделью и языком. Между контекстами задаются отношения: *Shared Kernel*, *Customer–Supplier*, *Conformist*, *Anti-Corruption Layer* и др.

Для платформы турниров логично выделить как минимум контексты: **Identity/Auth**, **User profile**, **Tournament**, **Bracket**, **Match**, **Notifications**. **NotificationService** — контекст «**сообщение пользователю**»: он **не является** источником истины по правилам турнира или результату матча, но **подписан** на факты из других контекстов (через API или события) и хранит **представление** этих фактов для UX. Связь с внешними объектами выражена через `RelatedEntity` + строковый тип — это осознанное **упрощение**: полная нормализация «матча» внутри NotificationService привела бы к дублированию bounded context Match.

## 6.3 Тактическое проектирование: строительные блоки

| Паттерн / понятие | Суть | Проявление в Eventide.NotificationService |
|-------------------|------|---------------------------------------------|
| Entity | Идентичность, жизненный цикл | `Notification`, `User`, `Administrator`, `RelatedEntity` |
| Value Object | Нет собственного ключа, сравнение по значению, иммутабельность логическая | `Title`, `Body`, `Username`, `RelatedEntityTypeName` |
| Aggregate | Граница согласованности | В первую очередь `Notification`; поведение прочтения внутри агрегата |
| Repository | Абстракция коллекции сущностей | Интерфейсы в `Domain.Repositories.Abstractions`, реализации EF |
| Domain event (концепт) | Фиксация факта в домене | В коде не развёрнуто; типичное расширение для публикации «NotificationCreated» |
| Factory | Сложное создание объекта | `Administrator.CreateNotification` |

## 6.4 «Богатая» доменная модель против анемичной

**Анемичная модель** — классы данных с публичными свойствами и сервисным слоем, который меняет состояние извне. **Rich domain model** — инварианты и переходы состояний инкапсулированы в сущностях (`MarkAsRead`, проверки в `User`). Проект курсовой демонстрирует **смещение в сторону rich model**, что согласуется с рекомендациями DDD и усложняет «случайные» изменения полей без бизнес-правил.

## 6.5 Clean Architecture Роберта Мартина

### 6.5.1 Правило зависимостей (Dependency Rule)

Внутренние круги (политики, сущности) **не зависят** от внешних (UI, БД, фреймворков). Зависимости направлены **внутрь**: инфраструктура реализует интерфейсы, объявленные ближе к ядру. Это повышает **тестируемость**: доменные правила можно проверять без PostgreSQL (как в `DomainApp`).

### 6.5.2 Соответствие слоёв проекту

| Слой (логический) | Проекты / артефакты |
|-------------------|---------------------|
| Domain (Entities + VO) | `NotificationService.Domain`, `NotificationService.ValueObjects` |
| Абстракции портов (доступ к данным) | `NotificationService.Domain.Repositories.Abstractions` |
| Infrastructure (адаптеры) | `NotificationService.Infrastructure.EntityFramework` |
| Presentation | `NotificationService.WebHost` |
| Демонстрация домена без БД | `DomainApp` |

**Источник:** Martin R. C. *Clean Architecture: A Craftsman's Guide to Software Structure and Design.* Prentice Hall, 2017.

**Дополнительно (Microsoft Learn, слоистые веб-приложения):** https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/

## 6.6 Гексагональная архитектура (Ports and Adapters)

Clean Architecture Мартина родственна **гексагональной** модели Кокбёрна: **порты** — интерфейсы (репозитории), **адаптеры** — EF, HTTP API, консоль. Разница в основном терминологическая; для курсовой важно, что **NotificationService.Domain** выступает как **ядро**, а EF — заменяемый адаптер (теоретически возможен другой ORM или хранилище).

## 6.7 Слой приложения (Application) и разрыв в текущем решении

Руководства Microsoft описывают цепочку **Presentation — Application — Infrastructure — Domain**. В данном проекте сборка **Application** не выделена: сценарии «создать уведомление», «получить ленту» должны будут жить в **сервисах приложения** (команды/запросы), координирующих репозитории и транзакции. Сейчас часть сценария имитирует `DomainApp`, часть — будущие контроллеры. **Риск:** протаскивание `DbContext` в контроллеры и размытие транзакционных границ — именно поэтому в разделе 5 зафиксировано требование постепенно ввести прикладной слой.

## 6.8 Entity Framework Core как инфраструктурный адаптер

### 6.8.1 Роль ORM в DDD-проекте

EF Core не является частью домена; это **технология персистентности**. Её задача — сохранить состояние агрегатов и восстановить их, не нарушая инвариантов при чтении. Ключевые приёмы в проекте:

1. **Fluent API** (`IEntityTypeConfiguration<T>`) — явная схема, удобная для code review.
2. **`HasConversion`** — маппинг value object ↔ скаляр без «расплющивания» домена в примитивы на всех уровнях.
3. **Shadow properties** — FK без загрязнения доменной модели; запросы через `EF.Property`.
4. **Миграции** — эволюция схемы с версионированием; `Database.Migrate()` на старте для dev.

### 6.8.2 Отслеживание изменений и транзакции

EF по умолчанию отслеживает сущности в контексте. В проекте `SaveChangesAsync` вызывается в базовом репозитории после операций — это упрощает код, но задаёт **границу транзакции** = одна операция репозитория. Для сценариев «создать уведомление + побочный эффект» в перспективе нужен явный `IDbContextTransaction` или паттерн Unit of Work.

### 6.8.3 Версии стека из репозитория

- **.NET 8** (`net8.0`)
- **EF Core 8.0.8**, **Npgsql.EntityFrameworkCore.PostgreSQL 8.0.8**

**Документация EF Core:** https://learn.microsoft.com/en-us/ef/core/

**Провайдер Npgsql:** https://www.npgsql.org/efcore/

## 6.9 Интеграция микросервисов: шаблоны, релевантные для уведомлений

| Шаблон | Идея | Применимость к NotificationService |
|--------|------|--------------------------------------|
| Choreography | Каждый сервис реагирует на события соседей | MatchService публикует событие → NotificationService создаёт запись |
| Orchestration | Центральный процесс координирует шаги | Реже для простых уведомлений; возможен BFF |
| Saga | Долгая распределённая транзакция с компенсациями | Если уведомление + списание бонусов должны быть согласованы |
| Outbox | Надёжная публикация событий из БД | Запись уведомления и outbox в одной транзакции — снижает потерю событий |

Текущая реализация фокусируется на **персистентной модели и API-хосте**; перечисленные шаблоны — **ориентир** для промышленного развития.

## 6.10 Антикоррупционный слой и контракты

При интеграции микросервисов DDD рекомендует **ACL**: преобразование «чужой» модели (DTO матча из MatchService) в команды/объекты домена уведомлений. Проект `Eventide.NotificationService.Contracts` резервирует место для **стабильных контрактов** (версионируемые сообщения, DTO), чтобы внешние изменения не ломали домен без явного маппинга.

## 6.11 Атрибуты качества и архитектура

Классификация **ISO/IEC 25010** (совместимость, надёжность, производительность, сопровождаемость и др.) связывается с решениями: **сопровождаемость** — через разделение слоёв и Fluent API; **производительность** — через индексы; **безопасность** — через будущие политики доступа к ленте. Архитектурный анализ в курсовой не обязан включать полный ATAM, но **явная связка** NFR из раздела 5 с архитектурными механизмами усиливает обоснованность.

## 6.12 Перечень теории для успешной реализации (расширенный)

1. **C# и .NET 8:** обобщённые типы, nullable reference types, async/await, первичные конструкторы.
2. **ООП:** инкапсуляция, композиция, исключения предметной области vs системные.
3. **DDD (тактика):** сущности, VO, агрегаты, репозитории, фабрики, спецификации (при необходимости).
4. **DDD (стратегия):** bounded context, контекстная карта, интеграционные отношения.
5. **Clean Architecture / гексагональная модель:** правило зависимостей, порты и адаптеры.
6. **EF Core:** модель, сопоставление, миграции, трекинг, транзакции, фильтрация запросов.
7. **PostgreSQL:** индексы, типы, изоляция транзакций (базовые сведения).
8. **ASP.NET Core:** DI, конфигурация, middleware, health checks (перспектива).
9. **Микросервисы:** идемпотентность, версионирование API, устойчивые шаблоны интеграции (outbox, retry).
10. **Тестирование:** модульные тесты домена без БД, интеграционные тесты с Testcontainers для PostgreSQL (перспектива).

## 6.13 Краткий вывод по разделу

Теория **DDD** обосновывает границы контекста и богатую модель уведомления. **Clean Architecture** и **гексагональная** модель объясняют разнесение проектов по слоям и использование репозиториев. **EF Core** выступает как технический адаптер с конвертерами и shadow FK. Для полного соответствия промышленным рекомендациям Microsoft следует **добавить слой Application** и интеграционные паттерны (очередь, outbox) поверх уже реализованного домена и инфраструктуры.

# 7. Программная реализация микросервиса «NotificationService»

## 7.1 Архитектура микросервиса (ветка InfrastructureLayer)

### 7.1.1 Архитектурный стиль

Реализация следует сочетанию **Clean Architecture** и **Domain-Driven Design**: ядро — доменная модель и абстракции репозиториев; периферия — ASP.NET Core Web API и адаптер персистентности на EF Core. Зависимости направлены **от инфраструктуры и представления к домену**, а не наоборот. Консольный проект `DomainApp` демонстрирует, что домен **не требует** наличия базы данных для проверки сценариев.

### 7.1.2 Уровень системы (логический контекст C4 «System Context»)

Внешние акторы и системы взаимодействуют с микросервисом уведомлений по сети. Типовая схема (упрощённо, в символах ASCII):

```
  [Пользователь]          [Администратор]
         \                      /
          \   HTTPS / JSON     /
           v                    v
    +-----------------------------------+
    |   NotificationService.WebHost     |  <-- ASP.NET Core, Swagger
    +-----------------+-----------------+
                      |  EF Core (Npgsql)
                      v
              +---------------+
              |  PostgreSQL   |
              +---------------+

  (будущее) MatchService / TournamentService ----event/API----> создание уведомлений
```

**Назначение блоков:** WebHost принимает HTTP-запросы и использует зарегистрированный `ApplicationDbContext` для чтения и записи; PostgreSQL хранит таблицы `Users`, `Administrators`, `Notifications`, `RelatedEntities`. Внешние доменные сервисы платформы на данном этапе **не подключены в коде**, но их место на схеме зафиксировано как точка расширения.

| `NotificationService.Infrastructure.EntityFramework` | EF Core 8 + Npgsql | Маппинг модели на БД, репозитории, миграции |
| `NotificationService.Domain` (+ ValueObjects, Repositories.Abstractions) | Чистый .NET | Правила предметной области и контракты доступа к данным |

### 7.1.6 Модель развёртывания

Минимальная конфигурация: один экземпляр процесса WebHost (контейнер Docker или служба Windows/Linux) и экземпляр PostgreSQL. Строка подключения передаётся через конфигурацию (`ConnectionStrings:ApplicationDbContext`). При старте вызывается `Database.Migrate()` — удобно для dev/staging; в production часто миграции выполняют отдельным шагом CI/CD.

### 7.1.7 Потоки выполнения (runtime)

1. **HTTP-запрос** → маршрутизация ASP.NET Core → (будущий) контроллер / минимальный API → репозиторий → `SaveChanges` / запрос LINQ → PostgreSQL.
2. **Старт приложения** → построение `WebApplication` → регистрация `DbContext` → `MigrateDatabase<ApplicationDbContext>()` → обновление схемы.
3. **DomainApp** → прямое создание сущностей в памяти → вывод в консоль (без шага 1 и 2).

### Листинг 7.1 — полная конфигурация EF: `NotificationConfiguration`

Источник: `Infrastructure/NotificationService.Infrastructure.EntityFramework/Configuration/NotificationConfiguration.cs`.

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;
using NotificationService.Domain;
using NotificationService.ValueObjects;
using NotificationService.ValueObjects.Validators;

namespace NotificationService.Infrastructure.EntityFramework.Configuration;

public class NotificationConfiguration : IEntityTypeConfiguration<Notification>
{
    public void Configure(EntityTypeBuilder<Notification> builder)
    {
        builder.HasKey(x => x.Id);
        builder.Property(x => x.Id).IsRequired();

        builder.Property(x => x.Title)
            .IsRequired()
            .HasConversion(title => title.Value, str => new Title(str))
            .HasMaxLength(TitleValidator.MAX_LENGTH);

        builder.Property(x => x.Body)
            .IsRequired()
            .HasConversion(body => body.Value, str => new Body(str))
            .HasMaxLength(BodyValidator.MAX_LENGTH);

        builder.Property(x => x.Type)
            .IsRequired();

        builder.Property(x => x.IsRead)
            .IsRequired()
            .HasDefaultValue(false);

        builder.Property(x => x.ReadAt)
            .IsRequired(false)
            .HasConversion(
                src => !src.HasValue
                    ? src
                    : src.Value.Kind == DateTimeKind.Utc
                        ? src
                        : DateTime.SpecifyKind(src.Value, DateTimeKind.Utc),
                dst => !dst.HasValue
                    ? dst
                    : dst.Value.Kind == DateTimeKind.Utc
                        ? dst
                        : DateTime.SpecifyKind(dst.Value, DateTimeKind.Utc));

        builder.Property(x => x.CreatedAt)
            .IsRequired()
            .HasConversion(
                src => src.Kind == DateTimeKind.Utc ? src : DateTime.SpecifyKind(src, DateTimeKind.Utc),
                dst => dst.Kind == DateTimeKind.Utc ? dst : DateTime.SpecifyKind(dst, DateTimeKind.Utc));

        builder.Property(x => x.RelatedEntityType)
            .IsRequired(false)
            .HasConversion(relatedType => relatedType != null ? relatedType.Value : null,
                str => !string.IsNullOrEmpty(str) ? new RelatedEntityTypeName(str) : null);

        builder.Property<Guid?>("AdministratorId");
        builder.Property<Guid>("RecipientUserId");
        builder.Property<Guid?>("RelatedEntityId");

        builder.HasOne(x => x.RecipientUser)
            .WithMany()
            .HasForeignKey("RecipientUserId")
            .IsRequired()
            .OnDelete(DeleteBehavior.Restrict);

        builder.HasOne(x => x.Administrator)
            .WithMany("_notifications")
            .HasForeignKey("AdministratorId")
            .IsRequired(false)
            .OnDelete(DeleteBehavior.SetNull);

        builder.HasOne(x => x.RelatedEntity)
            .WithMany()
            .HasForeignKey("RelatedEntityId")
            .IsRequired(false)
            .OnDelete(DeleteBehavior.SetNull);

        builder.HasIndex(x => x.CreatedAt);
        builder.HasIndex(x => x.IsRead);
        builder.HasIndex("RecipientUserId");
        builder.HasIndex("AdministratorId");
    }
}
```

**Пояснения к листингу 7.1.** (1) Класс реализует `IEntityTypeConfiguration<Notification>` — вся схема таблицы для агрегата в одном месте. (2) `Title` и `Body` мапятся через `HasConversion` из value object в строку с ограничением `HasMaxLength`, согласованным с валидаторами домена. (3) Для `ReadAt` и `CreatedAt` заданы двусторонние конвертеры, приводящие значение к `DateTimeKind.Utc` — это снимает двусмысленность при чтении из PostgreSQL. (4) Три объявления `builder.Property<Guid?>(...)` задают **теневые** внешние ключи: в классе `Notification` нет публичных свойств `RecipientUserId` и т.д., но в SQL они есть. (5) `OnDelete(Restrict)` для пользователя запрещает удаление получателя, пока существуют уведомления — сохранение истории. (6) Для администратора и `RelatedEntity` выбран `SetNull` — при удалении «якоря» ссылка обнуляется, текст уведомления остаётся. (7) Индексы поддерживают фильтрацию по дате, признаку прочтения и FK — типовые запросы ленты и счётчиков.

```csharp
    {
        if (recipientUser == null) throw new ArgumentNullValueException(nameof(recipientUser));
        if (title == null) throw new ArgumentNullValueException(nameof(title));
        if (body == null) throw new ArgumentNullValueException(nameof(body));

        if (relatedEntityType == null) throw new ArgumentNullValueException(nameof(relatedEntityType));
```

### Листинг 7.3 — обобщённый репозиторий `EfRepository<TEntity, TId>`

Источник: `Infrastructure/.../RepositoriesEF/EfRepository.cs`.

```csharp
using NotificationService.Domain.Base;
using NotificationService.Domain.Repositories.Abstractions.Base;
using Microsoft.EntityFrameworkCore;
using NotificationService.Infrastructure.EntityFramework;

namespace NotificationService.Infrastructure.EntityFramework.RepositoriesEF;

public class EfRepository<TEntity, TId>(ApplicationDbContext context)
        : IRepository<TEntity, TId>
        where TEntity : Entity<TId>
        where TId : struct, IEquatable<TId>
{
    public async Task<IReadOnlyCollection<TEntity>> GetAllAsync(CancellationToken cancellationToken = default)
        => await context.Set<TEntity>()
        .ToListAsync(cancellationToken);

    public virtual async Task<TEntity?> GetByIdAsync(TId id, CancellationToken cancellationToken)
        => await context.Set<TEntity>().FindAsync(new object[] { id }, cancellationToken: cancellationToken);

    public async Task<bool> ExistsAsync(TId id, CancellationToken cancellationToken = default)
        => await context.Set<TEntity>().AnyAsync(x => EqualityComparer<TId>.Default.Equals(x.Id, id), cancellationToken);

    public async Task AddAsync(TEntity entity, CancellationToken cancellationToken = default)
    {
        ArgumentNullException.ThrowIfNull(entity, nameof(entity));

        await context.Set<TEntity>().AddAsync(entity, cancellationToken);
        await context.SaveChangesAsync(cancellationToken);
    }

    public async Task UpdateAsync(TEntity entity, CancellationToken cancellationToken = default)
    {
        ArgumentNullException.ThrowIfNull(entity, nameof(entity));

        context.Set<TEntity>().Update(entity);
        await context.SaveChangesAsync(cancellationToken);
    }

    public async Task DeleteAsync(TEntity entity, CancellationToken cancellationToken = default)
    {
        ArgumentNullException.ThrowIfNull(entity, nameof(entity));

        context.Set<TEntity>().Remove(entity);
        await context.SaveChangesAsync(cancellationToken);
    }

    public async Task<bool> DeleteAsync(TId id, CancellationToken cancellationToken)
    {
        var entity = await GetByIdAsync(id, cancellationToken);

        if (entity is null)
        {
            return false;
        }

        await DeleteAsync(entity, cancellationToken);
        return true;
    }
}
```

**Пояснения к листингу 7.3.** (1) Один класс закрывает типовой CRUD для любой сущности с `Entity<TId>`. (2) После каждой мутации вызывается `SaveChangesAsync` — граница транзакции совпадает с одной операцией репозитория. (3) `FindAsync` используется для загрузки по ключу с учётом кэша контекста. (4) Специализированные репозитории наследуют этот класс и добавляют запросы предметной области (см. листинг 7.5).

### Листинг 7.5 — `EfNotificationRepository` (полный файл)

```csharp
using NotificationService.Domain;
using Microsoft.EntityFrameworkCore;

namespace NotificationService.Infrastructure.EntityFramework.RepositoriesEF;

public class EfNotificationRepository(ApplicationDbContext context)
    : EfRepository<Notification, Guid>(context)
{
    private readonly DbSet<Notification> _notifications = context.Set<Notification>();

    public async Task<IEnumerable<Notification>> GetNotificationsByUserIdAsync(
        Guid userId,
        CancellationToken cancellationToken,
        bool onlyUnread = false)
    {
        var query = _notifications
            .Where(x => EF.Property<Guid>(x, "RecipientUserId") == userId);

        if (onlyUnread)
            query = query.Where(x => !x.IsRead);

        return await query
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync(cancellationToken);
    }

    public async Task<int> GetUnreadCountAsync(Guid userId, CancellationToken cancellationToken)
    {
        return await _notifications
            .Where(x => EF.Property<Guid>(x, "RecipientUserId") == userId && !x.IsRead)
            .CountAsync(cancellationToken);
    }

    public async Task<IEnumerable<Notification>> GetNotificationsByAdministratorIdAsync(
        Guid administratorId,
        CancellationToken cancellationToken)
    {
        return await _notifications
            .Where(x => EF.Property<Guid?>(x, "AdministratorId") == administratorId)
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync(cancellationToken);
    }
}
```

```csharp
using Microsoft.EntityFrameworkCore.Metadata.Builders;
using NotificationService.Domain;
using NotificationService.ValueObjects;
using NotificationService.ValueObjects.Validators;

namespace NotificationService.Infrastructure.EntityFramework.Configuration;

public class UserConfiguration : IEntityTypeConfiguration<User>
{
    public void Configure(EntityTypeBuilder<User> builder)
    {
        builder.HasKey(x => x.Id);
        builder.Property(x => x.Id).IsRequired();
        builder.Property(x => x.Username)
            .IsRequired()
            .HasConversion(username => username.Value, str => new Username(str))
            .HasMaxLength(UsernameValidator.MAX_LENGTH);

        builder.HasIndex(x => x.Username)
            .IsUnique();
    }
}
```

**Пояснения к листингу 7.6.** Уникальный индекс по `Username` обеспечивает согласованность с ожиданиями UserService; конвертер VO гарантирует, что в столбец попадают только уже провалидированные имена.

### Листинг 7.7 — демонстрационное приложение `DomainApp` (полный `Program.cs`)


### Листинг 7.9 — применение миграций при старте

Источник: `Presentation/NotificationService.WebHost/Helpers/MigrationManager.cs`.

```csharp
using Microsoft.EntityFrameworkCore;
namespace NotificationService.WebHost.Helpers;

public static class MigrationManager
{
    public static IHost MigrateDatabase<T>(this IHost host) where T : DbContext
    {
        var scope = host.Services.CreateScope();
        var appContext = scope.ServiceProvider.GetService<T>();
        appContext?.Database.Migrate();
        return host;
    }
}
```

**Пояснения к листингу 7.9.** Создаётся scope DI, извлекается `DbContext`, вызывается `Migrate()` — схема БД приводится к последней миграции (`FixNotificationInfrastructure` и др.). В production обычно выносят в отдельный job; для учебного стенда приём ускоряет запуск.

### Листинг 7.10 — фабрика уведомления в домене (`Administrator.CreateNotification`)

Источник: `Domain/NotificationService.Domain/Administrator.cs` (фрагмент метода).

```csharp
public Notification CreateNotification(User recipientUser, Title title, Body body, NotificationType type, RelatedEntityTypeName? relatedEntityType = null, RelatedEntity? relatedEntity = null)
{
    var notification = new Notification(recipientUser, title, body, type, DateTime.UtcNow, this, relatedEntityType, relatedEntity);
    if (_notifications.Contains(notification)) throw new NotificationNotFoundException(notification.Id);
    _notifications.Add(notification);
    return notification;
}
```

**Пояснения к листингу 7.10.** Метод выступает **фабрикой** доменного объекта и связывает уведомление с автором через `this`; персистентность выполняется отдельно через репозиторий.

# 8. Заключение

В работе выполнен системный анализ места **микросервиса уведомлений** в экосистеме платформы турниров: определены границы ответственности, связи с Auth, User, Tournament, Bracket и Match сервисами, сформулированы функциональные и нефункциональные требования и пользовательские сценарии. Практическая значимость — в готовой основе для промышленного развития: контракты между сервисами, прикладной слой, интеграция по событиям и расширение каналов доставки.
